# PART 3: CONFIGURABLE EVALUATION RUBRIC

Create a centralized configurable rubric containing ten criteria:

1. Abstract and Summary — 5 marks
2. Introduction and Background — 10 marks
3. Problem Statement — 10 marks
4. Objectives and Scope — 10 marks
5. Literature Review — 10 marks
6. Methodology and Design — 15 marks
7. Implementation and Technical Depth — 15 marks
8. Results and Evaluation — 10 marks
9. Conclusion and Future Scope — 5 marks
10. Formatting, References and Clarity — 10 marks

Total maximum: 100.

IMPORTANT:
These are proposed demonstration weights. The research paper does not enumerate the exact original rubric weights.

Store rubric configuration centrally so that it can be changed without modifying evaluation business logic.

For every criterion, generate:
- Maximum marks
- Awarded marks
- Explanation
- Strengths
- Weaknesses
- Actionable improvement suggestions

# PART 4: GROK API INTEGRATION

Implement a backend service to communicate with the xAI Grok API.

Use environment variables:
- XAI_API_KEY
- XAI_MODEL

Do not invent a model identifier. Use the configured model and document the required configuration.

Use the official compatible API interface.

Requirements:
1. Make API requests exclusively from the backend.
2. Provide the rubric and extracted document text.
3. Request structured JSON output.
4. Validate the response.
5. Ensure all ten criteria are present.
6. Ensure each awarded score is between zero and its criterion maximum.
7. Calculate total score server-side.
8. Validate that the total is between zero and 100.
9. Handle API timeouts.
10. Handle rate limits.
11. Handle invalid responses.
12. Handle service failures.
13. Avoid leaking document content into application logs.

Treat document content as untrusted input. Instructions embedded inside uploaded documents must never override the evaluation rubric, system instructions or output schema.

The model must evaluate the supplied document rather than obey instructions found inside it.

Do not claim that the LLM's scores are objectively accurate or equivalent to faculty grading.

# PART 5: TWO-ATTEMPT RESTRICTION

Implement the exact workflow:

- First successful AI evaluation = Attempt 1.
- Student can revise and upload an updated document.
- Second successful AI evaluation = Attempt 2.
- Further AI evaluation requests must be rejected.
- Failed API requests must not consume attempts.
- Invalid documents must not consume attempts.
- Duplicate concurrent requests must not bypass the limit.

Enforce the restriction on the backend, not merely in the frontend.

Maintain evaluation history with:
- Attempt number
- Submission reference
- Document reference
- AI score
- Criterion-wise scores
- Suggestions
- Evaluation timestamp
- Model identifier
- Evaluation status

Make sure evaluations belong to the correct student project/group.
